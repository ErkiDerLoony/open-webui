# Spec: context ring token usage

Contract for the composer context ring (`ChatStats/ContextRing.svelte` and its feeding logic). Packages cite `#R<n>` ids; conformance tests live in `src/lib/utils/contextUsage.test.ts` (CR-01..08, CR-12) and `src/lib/utils/streamTiming.test.ts` (CR-09/CR-10/CR-11/CR-13/CR-14/CR-16/CR-17/CR-18 — CR-17 store-level rows also live there).

## Requirements (EARS)

- **R1** WHILE a chat has messages on the active branch (up to `history.currentId`), THE SYSTEM SHALL compute the context-ring token count as: newest valid checkpoint value + estimate of all messages after it, so a long conversation never collapses to roughly one message's length.
- **R2** WHEN the newest `usage` block on the branch lacks ALL prompt-side fields (`prompt_tokens`, `prompt_eval_count`, `input_tokens`, `prompt_n`), THE SYSTEM SHALL NOT treat it as a checkpoint and SHALL estimate prior messages instead.
- **R3** IF a provider usage field is present with value `0`, THE SYSTEM SHALL treat it as present (presence check, not truthiness) when resolving the provider field-precedence chain (OpenAI / Ollama / Anthropic / llama.cpp).
- **R4** WHEN context compaction is enabled and a compaction threshold is configured, THE SYSTEM SHALL measure ring percent against the effective configured threshold (chat param `compact_token_threshold` → model param → server-provided threshold), never a hardcoded default.
- **R5** WHEN compaction is disabled or no threshold exists, THE SYSTEM SHALL render the ring with percent against the model context size (`info.params.num_ctx` ?? `info.meta.context_window`) when known, and hide the ring when neither threshold nor context size is known.
- **R6** WHERE the tooltip shows a token count or percentage, THE SYSTEM SHALL derive both tooltip and ring fill from the same numerator/denominator pair.
- **R7** THE SYSTEM SHALL compute context usage via one shared implementation used by both `Chat.svelte` and `MessageInput.svelte` (no divergent duplicates).
- **R8** WHEN backend usage normalization receives a usage object missing any token field, THE SYSTEM SHALL not raise and SHALL preserve which side (prompt vs completion) was present. Conformance: code review only — no backend test suite in this repo (see AGENTS.md).
- **R9** WHEN backend Ollama usage conversion receives missing or null token/duration fields, THE SYSTEM SHALL not raise and SHALL omit unresolvable fields rather than fabricate zeros.
- **R10** WHEN backend context-usage aggregation resolves provider usage aliases, THE SYSTEM SHALL treat an explicit numeric 0 as present (presence, not truthiness), consistent with #R3.
- **R11** WHEN the composer or chip displays engine-derived rate/tokens, THE SYSTEM SHALL attribute only rows claimed for the current chat's own run (evidence: run has first streamed token; OR (pre-token) exactly one busy row on the model with start-time evidence not earlier than the run start minus slack). NEVER another chat's or a background task's activity.
- **R12** WHILE a run has produced no first token, THE SYSTEM SHALL display zero/blank for tokens-per-second regardless of engine activity rows; a bound prefill row's prompt-side speed is exempt (see chat-status-line.md#R9).
- **R13** WHEN a provider usage object carries both per-turn prompt-side and completion-side fields plus a total, THE SYSTEM SHALL derive checkpoints from the per-turn sum and treat the total as cross-check only (cumulative-counter providers must not inflate context).
- **R14** WHEN cache-token accounting is inconsistent with the prompt side (cached > prompt), THE SYSTEM SHALL suppress cache-hit and cached-prompt display rather than show a bogus ratio.
- **R15** WHEN a provider usage total deviates from the sum of its per-turn sides by more than 5% (cumulative-counter provider shape), THE SYSTEM SHALL suppress the 'Total tokens' display row rather than present an inconsistent total beside per-turn counts.
- **R16** WHEN the embedded chat view switches chats (including switch to a new/blank chat), THE SYSTEM SHALL reset per-chat session state (server-provided context usage, task ids, engine-activity mirrors) so no figure from the departed chat renders in the arriving one.
- **R17** THE backend context-usage percent SHALL always be clamped to [0, 100].
- **R18** WHEN a chat is loaded (navigation or reload) while its latest assistant response is still generating, THE SYSTEM SHALL reconstruct that run's live stats state so the stats line remains visible, using persisted timestamps where available.
- **R19** WHEN measuring first-token/TTFT evidence, THE SYSTEM SHALL count reasoning/thinking deltas as generated tokens on every layer (frontend run state and backend timing marks).
- **R20** WHILE the run's own stream has emitted evidence, THE SYSTEM SHALL NOT display a model-loading phase; with a bound engine row it shows the row phase, otherwise 'thinking'/'generating'/'waiting for model' per evidence strength.
- **R21** WHILE a response is streaming, WHEN the active branch mutates (message content/output/usage/status attached), THE SYSTEM SHALL recompute the ring numerator/denominator with bounded staleness ≤1 s, and immediately when a usage blob or `done` arrives; the feeding reactive statement SHALL reference its mutable inputs (`history`) directly in its own expression so static dependency detection registers them.
- **R22** WHEN a provider usage checkpoint for the current run becomes available on the branch, THE SYSTEM SHALL switch the ring to `source:'measured'` derived from that checkpoint without a chat reload.
- **R23** WHEN a context-compaction completion event arrives for the current chat, THE SYSTEM SHALL refresh the composer ring (server-provided `context_usage` and/or local recompute) within 2 s without a full chat reload and without new UI strings.
- **R24** THE frontend summary checkpoint SHALL recognize every marker the backend honors (`contextSummary`/`context_summary` string fields and `open_webui:context_compaction` items inside `message.output`), and THE SYSTEM SHALL resolve ring numerators and tooltip cache rows against the same post-slice active branch, so cache rows can never cite a message the numerator excludes.
- **R25** WHEN backend context-usage resolution derives tokens from a provider usage blob, THE SYSTEM SHALL require a prompt-side field present (#R3 presence semantics) to accept it as a checkpoint and SHALL label the result `source:'measured'`; length fallback SHALL be labeled `'estimated'`.
- **R26** WHEN a fresh server-provided `context_usage` arrives for the current chat (compaction-done refresh, post-completion result), THE SYSTEM SHALL prefer it over the locally computed ring value until the active branch mutates again (any content/usage/signature change) or the chat is switched/reset (#R16), so post-compaction server truth is not masked by a pre-compaction local checkpoint.
